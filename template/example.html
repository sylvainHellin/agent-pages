Design decisions learned lately

The guiding rule since 23 September

The core keeps only what every note shares; everything a team may want to organise differently is a swappable template. From the September design review
DecisionWhat it says
D20, D21Habitat, weather, status and note-kind lists leave the core; the core keeps bare fields such as kind. This settles the "habitat in the core?" question.
D22The role field is gone: a membership links a person to a project and lists what they may edit.
D23One note table; per-kind fields go into templates, observation first (observation.json).
D24A field's name follows its template: observation fields start with obs_, enforced by check.py.
D25Site and project code become records; file extension stays text.
D26Every link between people sits in one tree under the project. A role relative to one note goes on the link, never on the person: a team lead both assigns and is assigned.
D27What a note is about and where it was taken are two fields: subject points at a kind (bird, plant), place at a real spot (north bank, pool 2). Places nest; projects reach them through their sites, since a site outlives its projects.

Smaller lessons

  • Field naming: has plus a role noun is fine (hasReviewer), has plus a type name reads as ownership and takes a verb instead (involvesPerson).
  • A note kind says what the note is, never its subject, author, status or project.
  • The phone's GPS has no altitude field indoors, contrary to what the docs claimed.
  • Code C means cloudy in one template and coastal in another and already misfiles nine notes.
  • The ten onboarding questions were reworded in the tester's voice (13 October).
